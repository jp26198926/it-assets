# Investigation: /tickets Page Data Loading Flow

## Summary

**Your concern is valid.** The `/tickets` page currently loads ALL matching records from MongoDB into the frontend and does client-side filtering, sorting, and pagination. There is NO server-side pagination.

---

## How It Works Today

### Initial Page Load
```
page.tsx (useEffect on mount)
  → getTickets({ default_view: true })  [Server Action]
    → ticket-service.ts getTickets()
      → TicketModel.find(query).sort({ created_at: -1 }).lean()
      → Returns ALL matching tickets (no .limit() or .skip())
    → Returns full Ticket[] to client
  → setTickets(data) — entire array stored in React state
```

The `default_view: true` filter limits results to:
- Tickets with status **"Open"** or **"In Progress"**, OR
- Tickets **created today** (timezone-aware)

But within that filter, **every matching record is returned** — no cap.

### What Happens Client-Side (All In-Memory)
| Feature | Where it runs | Mechanism |
|---------|--------------|-----------|
| Pagination | Client | TanStack `getPaginationRowModel()` — slices in-memory array |
| Sorting | Client | TanStack `getSortedRowModel()` |
| Column filtering | Client | TanStack `getFilteredRowModel()` |
| Global search (typing) | Client | TanStack `globalFilter` |
| Advanced Filter ("Adv Filter") | Client | Custom `useMemo` on already-fetched data |

### What Does Hit the Server
| Action | Trigger | What happens |
|--------|---------|-------------|
| Search bar + Enter | `onServerSearch({ search: value })` | New server action call with `$regex` filter |
| Advanced Search dialog | `onServerSearch(filters)` | New server action with multiple MongoDB filters |
| Clear button | `onServerSearchClear()` | Resets to `{ default_view: true }` and re-fetches |

These replace the entire `tickets[]` state with fresh results — but still return ALL matching records with no pagination.

---

## The Problem

If a user has 5,000 Open/In Progress tickets, the initial load fetches all 5,000, sends them over the wire, and stores them in React state. The browser then handles pagination (showing 10 at a time), sorting, and filtering — all on that 5,000-record array.

This is inefficient because:
1. **Network**: Transfers potentially large payloads unnecessarily
2. **Memory**: All records held in browser memory
3. **Render**: TanStack Table processes the full array for sort/filter on every interaction

## Questions for You

1. **Do you want to implement server-side pagination?** This would mean the service returns `{ data: Ticket[], total: number, page: number, pageSize: number }` instead of `Ticket[]`, and the client sends `page`/`pageSize` on every request.

2. **Should server-side sorting also be added?** Currently sorting is purely client-side via TanStack Table.

3. **What's the expected data volume?** If tickets rarely exceed a few hundred, the current approach may be acceptable. If it can grow to thousands+, server-side pagination becomes important.

4. **Should the "default_view" initial load also be paginated?** Or is the current subset (Open/In Progress + today) small enough to load all at once?

5. **Should the Advanced Filter ("Adv Filter") also become server-side?** Or is it acceptable to keep that as client-side filtering on the current page of results?
