## Overview

Design a Minutes of Meeting recording module for the IT Assets project. The module follows the project's established entity pattern (Mongoose + MongoDB) with the following user requirements:

- **Standalone action items** (separate entity, not embedded)
- **User-defined meeting types** (separate MeetingType entity)
- **Recurring meetings** (recurrence rules + parent/child linking)
- **Cloudinary file attachments** (reuse existing upload pattern)
- **Embedded attendee subdocuments** (tightly coupled to meeting)

## Timezone Integration

Meeting dates are stored as UTC `Date` objects in MongoDB. All date display and filtering respects the app-level timezone setting from `Application.timezone`.

**Service layer** (`meeting-service.ts`):
- Import `startOfDayInTimezone`, `endOfDayInTimezone` from `@/lib/utils/timezone`
- Import `getAppSettings` from `@/lib/services/application-service`
- For date-range filters (`scheduled_date_from`, `scheduled_date_to`), convert user input dates using `startOfDayInTimezone` / `endOfDayInTimezone` with the app timezone (same pattern as `ticket-report-service.ts` and `ticket-service.ts`)

**UI layer**:
- Use `formatInAppTimezone` from `@/lib/utils/timezone` to display `scheduled_date` in the configured timezone
- The meeting form should accept date/time input in the user's local timezone, and the service converts to UTC for storage

**Action items**: Due dates follow the same pattern — stored as UTC, displayed/filtered using app timezone.

## Key Design Decisions

1. **Recurring meetings**: When a recurring meeting is created, only the first instance is stored. Future instances are generated on-demand or via a background job. `parent_meeting_id` links instances back to the original. The `recurrence` config lives only on the parent.

2. **Agenda items + attendees as embedded subdocuments**: Follows the Role-permissions pattern. Use `$push`/`$pull` for add/remove, manual dedup (not `$addToSet`).

3. **Action items as standalone**: Allows querying "all action items assigned to me across all meetings" — a common use case that would be impossible with embedding.

4. **Meeting attachments**: Reuse the ticket upload pattern — API route with FormData → Cloudinary streaming → store URLs as `string[]` on the meeting document.

5. **Meeting number auto-increment**: Uses the existing Counter model (like `ticket_no`) for `meeting_no`.

6. **Status flow**: Scheduled → In Progress → Completed (or Cancelled from any state).

7. **Timezone-aware dates**: All dates stored as UTC; displayed and filtered using the app's configured timezone via `formatInAppTimezone` / `startOfDayInTimezone` / `endOfDayInTimezone` utilities.
